## WinUI 3 Spike Specification: PDF + Pen Annotation Test App

### Goal

Build a small WinUI 3 desktop app that reproduces the current Electron PDF pen spike closely enough to evaluate whether WinUI 3 can support the core interaction model for the eventual Indico slide note-taking app.

This is **not** the full app. It is a focused spike to test:

PDF rendering, page scrolling, pen input over PDF pages, erasing, undo/redo, palm rejection, and basic stroke/page association.

---

# 1. App Identity

Working title:

**Indico Pen Spike**

The app should open as a normal Windows desktop application with a standard title bar.

The initial empty state should show a centered message similar to:

```text
PDF Pen Spike

Open a local PDF, then try pen input, erasing, undo, redo, palm rejection,
and scrolling.
```

Exact styling does not matter, but the app should look like a simple document annotation tool.

---

# 2. Top-Level Layout

The app should have three vertical regions:

```text
Window title bar
Menu bar
Toolbar
Scrollable PDF/document area
```

## Menu bar

Include a simple menu bar with:

```text
File   Edit   View   Window   Help
```

Only `File > Open PDF` needs to do anything for this spike.

## Toolbar

The toolbar should appear below the menu bar and contain:

```text
[Open PDF]   [Mouse/Pen mode indicator]   [Undo]   [Redo]          [Pointer/debug status]
```

The current Electron version has:

```text
Open PDF   ○ Mouse   Undo   Redo                 No pointer input yet
```

For WinUI, this can be approximate.

The toolbar should remain visible while the document scrolls.

---

# 3. PDF Loading

The app shall allow the user to open a **local PDF file** using a file picker.

After opening a PDF:

The app displays the filename above the first rendered page, for example:

```text
2026-05-28 - Vibe Plotting.pdf
```

The app should render the PDF as a vertical, scrollable document.

The spike should support PDFs at least up to about **100 pages**.

The implementation should prefer reasonably high-quality rendered pages over minimal memory usage, but it does not need to be production optimized.

---

# 4. PDF Display

Each PDF page should be rendered as a page-sized image or visual surface inside a scrollable region.

Pages should be displayed vertically, one after another.

The app should preserve page aspect ratio.

The page should be centered or left-aligned inside the available document area. Exact alignment is not critical.

There should be visible padding around the page, similar to the Electron spike.

The background outside the page can be light gray.

The app should work with slide-style PDFs where pages are landscape 16:9.

---

# 5. Annotation Layer

Each rendered PDF page shall have an annotation layer placed directly above it.

The annotation layer must accept pen strokes.

The coordinate system for saved strokes should be page-relative, not screen-relative.

For each stroke, store at minimum:

```text
page number
list of points
pen color
pen thickness
input type if available
```

For this spike, the pen color should be **black**.

The default pen thickness can be fixed. A reasonable value is fine.

No color picker is needed.

No stroke export format is required for this spike unless trivial.

---

# 6. Pen Input

The primary test is whether WinUI 3 supports natural pen annotation over a rendered PDF page.

The app should support:

```text
Pen down
Pen move
Pen up
Stroke rendering while drawing
Stroke remains after completion
```

The pen should draw directly on top of the visible PDF page.

The app should not require entering a special drawing canvas separate from the PDF.

The user should be able to write naturally on slides.

---

# 7. Mouse Input

Mouse behavior should be available for testing.

There should be an indicator showing the current active pointer type, similar to:

```text
Mouse
Pen
Touch
No pointer input yet
```

In the Electron spike, the debug text shows detailed pointer information. The WinUI spike should include some equivalent debug/status text, for example:

```text
pointer: mouse | button: left | pressure: 0.00 | mode: ink
```

Exact content is not important, but the app should expose enough information to debug whether the input is being interpreted as mouse, pen, or touch.

Mouse may draw in the spike, but pen behavior is the main concern.

---

# 8. Touch and Palm Rejection

The app should allow normal scrolling without accidentally creating ink strokes.

Desired behavior:

```text
Pen draws.
Touch scrolls.
Palm/touch contact during pen use should not create extra strokes.
```

This is one of the key things to evaluate.

It is acceptable for the spike to display diagnostic information about touch/palm input.

---

# 9. Scrolling

The PDF document area must be vertically scrollable.

Scrolling should work with:

```text
Mouse wheel / trackpad
Touch scrolling
Scrollbar
```

Pen drawing should not break scrolling.

When the user is not actively drawing, the document should behave like a normal scrollable PDF/document viewer.

---

# 10. Eraser

The app shall support an eraser mode.

Minimum acceptable behavior:

```text
Switch to eraser
Tap/cross a stroke to remove it
```

A more refined stroke-partial eraser is not required.

The goal is to test whether pen + eraser workflows are practical in WinUI.

---

# 11. Undo / Redo

The app shall provide Undo and Redo buttons.

Undo should remove the most recent annotation action.

Redo should restore the most recently undone action.

At minimum, undo/redo must work for completed strokes.

If erasing is implemented, erase actions should also participate in undo/redo if practical.

The toolbar buttons should be disabled or visually inactive when no undo/redo action is available.

---

# 12. Stroke Count / Debug Display

After a PDF is loaded, show a small status value near the top of the document or toolbar such as:

```text
0 strokes
3 strokes
```

This should reflect the current number of stored annotation strokes.

The Electron spike shows this near the filename/page area; the WinUI spike can place it anywhere visible.

---

# 13. Persistence

For this spike, full persistence is not required.

It is acceptable for annotations to disappear when the app closes.

However, the internal data model should already associate strokes with pages so that future save/load behavior would be possible.

---

# 14. Explicitly Out of Scope

Do not implement these in the WinUI spike:

```text
Indico integration
Downloading PDFs from Indico
Authentication
Meeting/session navigation
Markdown notes
Exporting notes
Exporting annotated PDFs
Multiple documents
Pen color selection
Pen thickness selection
Search
Bookmarks
Thumbnails
OCR
Cloud sync
```

---

# 15. Success Criteria

The spike is successful if one can:

```text
Open a local slide PDF.
Scroll through the rendered pages.
Draw black pen strokes on top of a page.
Erase strokes.
Undo and redo strokes.
Use touch/scrolling without accidental ink in normal use.
See basic pointer/debug status.
Confirm strokes are associated with the correct PDF page.
```

The main question this spike should answer is:

**Is WinUI 3’s pen, touch, and rendering support good enough to build the full Indico-based annotated slide note-taking app?**

## 16. Cursor and Tool Feedback

The application shall provide clear visual feedback indicating the current input tool.

### Mouse Mode

When the pointer is a mouse and annotation is enabled:

```text
Cursor: Crosshair
```

The crosshair should make it obvious where ink will be placed.

### Pen Mode

When a pen is hovering above the display:

```text
Cursor: Small pen tip indicator or crosshair
```

The exact appearance may depend on WinUI capabilities.

Requirements:

* Cursor position should accurately indicate ink placement.
* Hovering pen should be detectable if the hardware supports hover.
* The status area should indicate that pen input is active.

Example:

```text
pointer: pen
```

### Eraser Mode

When the eraser tool is selected:

```text
Cursor changes to eraser indicator
```

Acceptable examples:

* Small square
* Circle
* Eraser icon
* Any clearly different cursor

The user should be able to tell immediately that erasing rather than drawing will occur.

### Touch Input

Touch input generally has no visible cursor.

When touch interaction is active:

```text
No cursor required.
```

The status display should indicate:

```text
pointer: touch
```

### Cursor State Changes

Cursor/tool feedback should update immediately when:

```text
Pen tool selected
Eraser tool selected
Mouse enters document area
Pen enters hover range
Touch interaction begins
```

### Diagnostic Display

For debugging purposes, the application should display the resolved input type.

Examples:

```text
pointer: mouse
pointer: pen
pointer: touch
pointer: eraser
```

This information is intended to help determine how WinUI classifies the incoming hardware events.

---

For the spike specifically, I would also add one very important test requirement:

> **If the pen supports an inverted eraser (the eraser end of the stylus), the application should attempt to detect it and automatically switch to erase mode.**

That is a very common workflow in OneNote, Drawboard PDF, Journal, and other Windows ink applications, and it is something worth validating early in WinUI. If WinUI handles it naturally, that is a strong signal that the platform is a good fit for the larger application.
